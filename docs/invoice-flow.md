# 发票申请与余额扣点

管理员在发票设置中配置开票项目名称、最低申请金额和扣点比例。比例支持 0–100%，精度为 0.01 个百分点；后台用 `invoice_setting.fee_rate_basis_points` 保存基点，例如 3% 为 300。新配置默认 0%，升级不会自动对旧申请补扣余额。

## 申请、审核和取消

1. 用户从自己的已支付订单中选择申请，最多 100 笔。服务端重新检查订单归属、支付状态、申请期限和是否已经关联其他申请。提交的金额、费率、扣款额度不能覆盖服务端计算。
2. 申请金额来自订单真实付款快照。每笔订单先按系统汇率换算为开票币种、舍入到分，再汇总并按配置比例计算扣点。例如实付人民币 50.00 × 3% = 1.50，发票金额仍为人民币 50.00；实付 50 USD、人民币汇率 7.5 时，开票金额为人民币 375.00，扣点为人民币 11.25。
3. 申请时直接扣余额。金额转换为额度时向上取整到最小额度单位，余额恰好充足可以申请；不足返回“额度不足”。扣余额、申请、订单关联及收费记录在同一数据库事务内完成，任一写入失败均回滚。
4. 管理员批准后直接进入可开票状态，不再调整扣点或生成单独付款。原有上传 PDF/PNG/JPEG、邮件发送和用户文件查看流程继续使用。
5. 驳回时退回申请时实际扣除的额度，并保留申请及退款快照。用户取消或管理员删除未开票申请时，也在同一事务内退费并释放订单关联。取消后该申请从列表移除，原订单可以重新申请；已驳回申请可以取消以释放订单。
6. 已上传发票文件、已发送发票邮件或已经开票的申请不能取消退费。文件已保存但邮件发送失败时，同样保留申请，允许重试邮件。

退款使用 `charged_quota - refunded_quota`，不按当前费率、汇率或额度单位重新计算。重复驳回、重复取消、驳回后删除以及并发操作不会重复退费；退款会使钱包超过额度上限时，操作整体失败并保留申请。扣费和退款日志记录申请编号、货币金额及实际额度变动。

开启 Redis 时，申请先原子预留缓存中的可用额度，再在申请事务中扣除数据库余额。这样即使 API 消费尚在批量落库队列中，也不会凭过时的数据库余额放行。事务失败会尝试补偿缓存预留，成功后不再重复扣缓存；缓存不可用时收费申请会返回错误。如果补偿时 Redis 本身发生故障，会记录包含用户和额度的错误，供核对修复；数据库事务中的余额和申请记录仍整体回滚。

## 货币与历史数据

新申请的货币跟随系统的 USD/CNY/CUSTOM 额度显示设置，自定义货币同时保存符号；Tokens 显示模式下，发票仍以钱包基础货币 USD 计价。每笔申请保存自己的货币、费率和实际扣款快照，后来修改系统设置不会改写已申请发票或退款额度。

`TopUp.Money` 在不同渠道含义不同，例如 Stripe 将它用于计算充值额度，不能当作真实现金付款金额。本次新增 `paid_amount_minor` 和 `paid_currency` 保存已验证成功付款的原币种最小单位金额，保留原 `Money` 和充值额度计算。发票列表返回单独的 `invoice_amount_cents`、`currency`、`currency_symbol`，创建时重新核对并保存原金额、换算金额及汇率快照。

目前支持将有可信付款记录的 USD/CNY 订单换算为系统 USD/CNY/CUSTOM 开票币种。系统没有任意外币汇率表，因此其他原币种不会被猜测换算。旧充值没有付款快照时不直接按当前商品配置、赠额或系统显示币种补造金额；成功订阅订单如保留完整付款回执，可以据此核实。无法核实的订单不会列为可选订单，直接提交它们也会失败。Epay 的现有记录及协议调用没有明确币种，本次不会自动认定为人民币；这些订单需先确认本站实际支付口径或付款凭证。

Stripe、Creem、Waffo、Waffo Pancake 的新成功付款会尽可能保存已验签回执中的实付金额与币种。回执缺失、无效或币种无法核实时，不改变原有充值入账，但该订单不能自动开票；重复付款通知不会覆盖已经保存的快照。

Waffo Pancake 的平台验签通过后，还必须确认回执属于后台配置的商店。充值和订阅付款都需要配置商店 ID，订阅商品应属于该商店；商店为空或回执来自其他商店时，不接受付款回调。旧订阅回执用于开票时执行同样的归属检查，缺少商店信息的旧回执不会自动成为开票依据。

升级前的记录保持原有字段和关联：

- 旧待审核申请批准后直接可开票，不再要求新的补款；历史估算保留供查询，最终新增扣点为 0。
- 升级前已经发起的外部付款仍可通过原验签回调完成。未发起活动付款的旧待付款申请可以取消后重新申请。
- 旧外部支付不会凭空退入钱包；旧已开票记录继续受保护。

该仓库没有发布标签或 GitHub release。迁移回归采用改动前的 `15227624eaa558f66a2e4864301b44dc49b82b8e` 发票结构，其结构与本次任务初始 `2e415c6c69fc4959712c7eedabcbef9f802d178c` 相同。

迁移测试覆盖 SQLite 3.50.4、MySQL 9.6.0、PostgreSQL 17.9 的新建、旧结构升级和重复迁移，并校验原数据、唯一约束及索引。SQLite 旧结构在原版本重复迁移时就会重建订单关联和付款订单表；升级后仍存在这项原有行为，但没有新增重复重建，新增字段只增加一次。MySQL 和 PostgreSQL 的第二次升级迁移均不再执行 DDL。

## 接口与验证

现有申请、列表、审核、上传和文件接口保持路径不变。新增已登录用户接口：

```text
POST /api/invoice/applications/:id/cancel
```

服务端使用登录用户身份核对申请归属；客户端的 `can_cancel` 仅是显示提示，取消事务中会再次校验状态。原 `POST /api/invoice/applications/:id/pay` 对本人的有效申请返回 HTTP 410，不再创建付款；原付款方式列表返回空数组。外部通知和回跳接口保留处理升级前的在途付款。

本功能的主要回归命令：

```sh
go test -race ./model -run '^(TestInvoiceFee|TestReserveInvoiceFeeCache|TestTopUpPaymentReceipt)' -count=1 -v
go test ./service -run 'Test.*Invoice' -count=1
go test -race ./service -run 'Test.*Invoice' -count=1
go test ./controller -run '^TestInvoiceApplicationController' -count=1
```

真实 MySQL/PostgreSQL 测试通过 `TEST_MYSQL_DSN`、`TEST_POSTGRES_DSN` 启用，必须指向空的、以 `_test` 结尾的隔离数据库。测试会创建并清理自己的表；不要指向业务数据库。SQLite 使用每次测试独立的临时文件。
